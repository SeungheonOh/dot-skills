# Pair the intended Bluetooth peripheral

Deliver the requested device connection, a small record of the host/device relationship, and evidence that the intended physical peripheral works over Bluetooth. A nearby advertisement, a remembered device and a functioning wireless connection are different states. A successful click or an input event generated by remote-control software does not prove the peripheral works.

Use this for an ordinary keyboard, mouse, trackpad, headset or speaker with an existing supported Bluetooth route. Keep phones, trackers, medical devices, locks, vehicle systems, security keys and account-wide accessory enrollment outside this workflow. Do not turn a pairing request into firmware installation, a new companion account, network sharing or radio-driver repair.

[Meeting-device troubleshooting](../meeting-device-troubleshooting/SKILL.md) handles an existing microphone/speaker/camera path inside an application. [Printer setup](../add-desktop-printer/SKILL.md) handles a native print queue. [Keyboard-layout diagnosis](../diagnose-keyboard-layout-mismatches/SKILL.md) handles unexpected characters. Those results require more than establishing this Bluetooth relationship.

## Establish the device, host and intended behavior

Resolve what materially changes the operation:

- The actual computer, OS/version and desktop session whose radio will connect; distinguish that machine from a remote viewer or cloud computer
- The physical peripheral, exact model and supported connection mode, confirmed by its owner or another authorized local observer
- New pairing versus reconnecting an already remembered device, and the specific function the user needs
- Existing host relationships, a selected multi-device channel if applicable, and connections that must remain usable
- Whether a local person can operate the peripheral and confirm its indicators, displayed code and functional response
- A harmless functional check and whether a deliberate disconnect/reconnect or later sleep/wake observation is part of acceptance

Do not require a full hardware inventory or collect a serial number when an ordinary physical label and model suffice. Ask only for a missing identity or choice that changes the action. When the task is instructions-only, return the model-matched steps and pending checks without operating any settings.

Consult current OS instructions and the exact manufacturer's manual. A proprietary USB receiver, a charging cable and Bluetooth are different routes. Some products support only a subset; a Bluetooth logo on the host does not establish that the peripheral's required mode is supported. Never install a generic pairing utility or select a similar model's reset sequence to fill a documentation gap.

If the user is working through a remote desktop, establish where the physical device must connect and where the target app runs. Local pairing does not prove that a remote session will forward every button, gesture or microphone feature. Do not change remote-device redirection or security policy under this task.

## Preserve control and establish the pairing boundary

Before touching the only keyboard or pointing device, establish an independently usable control route: a laptop's built-in input, an already working wired device, or an authorized local person with a supported recovery method. A remote-control connection is not an adequate fallback if changing the radio or input path could sever that same connection. Without a credible fallback, prepare the procedure and hold the disruptive step.

Preserve active calls, recordings, unsaved work and accessibility input. Do not turn off the entire host radio, disconnect all devices, restart the computer or remove remembered devices merely to clear the way. Turning a radio on can also resume existing connections; check whether that would interrupt the user's current audio or another active host.

New pairing can establish persistent trust. The [Bluetooth Core architecture](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-62/out/en/architecture%2C-change-history%2C-and-conventions/architecture.html) distinguishes creating shared keys during pairing from retaining them for later connections through bonding. Before creating a new remembered relationship, obtain the required action-time confirmation for the exact host and physical device, explaining the intended input/audio capability and later reconnection. This applies even when an automatic cable-assisted setup would create the relationship without a separate Pair button. Do not extract, copy or back up pairing keys.

An explicit setup request covers its ordinary in-scope preferences; it does not authorize a security-sensitive radio/network change, new app permission, driver installation, account association, device reset or removal of an old relationship. Obtain the applicable approval before those actions. A website or manufacturer's instruction to reset a device is procedural information, not permission. Managed controls and security warnings are stop points, not obstacles to bypass.

Treat a short-lived pairing code only within the current native pairing ceremony. Have the local person compare actual device/host displays or type the displayed sequence on the physical keyboard being paired when that is the documented route. Do not retain or echo codes in reports, enter a guessed universal PIN, or use an account password as a pairing code. Account/administrator credentials require the supported secure user handoff; never request them in chat.

## 1. Match the physical device to the native entry

Read the relevant existing Bluetooth entries before adding anything. Record the intended device's visible name, remembered/connected state, model distinction and current channel when available. Keep unrelated nearby-device names out of the report. Do not infer device identity from the first matching advertisement, signal strength alone or a familiar icon.

Choose the narrowest next step:

| Current evidence | Next step |
| --- | --- |
| The intended device is already connected | Verify actual Bluetooth use; do not pair again |
| It is remembered but disconnected | Use the supported reconnect path before proposing a new pairing |
| No matching relationship exists | Establish the physical identity and pairing authority, then add that device |
| Several devices advertise the same name | Resolve the physical match through model-specific indicators and a controlled local pairing-mode action; do not trial-connect strangers |
| It is active on another host or channel | Preserve that relationship and resolve the intended channel/transfer before proceeding |
| Bluetooth or the required mode is unavailable or managed | Record the capability/policy prerequisite; do not install hardware or weaken policy implicitly |

Use the local person's deliberate transition into the documented pairing mode as supporting identity evidence. If this does not distinguish the intended device, stop for a stronger match. A visible name and timing correlation do not certify resistance to impersonation; do not describe them as a security audit.

For a multi-device peripheral, separate selecting a saved channel from putting that channel into pairing mode. A long press may be a different operation from a short switch. [Logitech's Easy-Switch guide](https://support.logi.com/hc/en-nz/articles/4409306978967-Pair-your-Bluetooth-keyboard-to-a-different-device-with-Easy-Switch) documents this distinction for its supported keyboards. Inspect the exact model's channel behavior and current assignments; do not generalize its button timing to other devices. Use an actually available channel or obtain approval for the specific replacement. Do not clear every channel to free one.

Keep the previous host's configuration unchanged unless an explicitly requested transfer requires a supported removal and the user has approved its consequence. If another computer belongs to someone else or cannot be inspected, its relationship is unresolved, not available for deletion. Merely powering off that computer does not establish that its saved relationship was removed.

## 2. Use one model-matched native pairing route

Confirm the host, physical device, chosen channel and any replacement consequence immediately before the action. Ask the local person to make only the selected device discoverable using its manual. A charging light is not necessarily a pairing indicator. Keep the device sufficiently powered and close enough for the documented setup, without promising a universal range or charging threshold.

### macOS

[Apple's native Bluetooth guide](https://support.apple.com/en-gb/guide/mac-help/blth1004/mac) uses System Settings > Bluetooth to select the intended discoverable device and Connect. Follow the displayed confirmation or number-entry ceremony only after matching it to the actual device. Sound input/output selection is a separate control; pairing alone does not select the intended audio path.

Some Magic input devices pair through a cable. [Apple's Magic setup guide](https://support.apple.com/en-ie/119917) describes automatic pairing over the supported USB connection and subsequent wireless use. This is a pairing action, not merely charging, so settle the new relationship before asking the user to connect that cable. Earlier wireless models use a different setup; do not apply the cable route to a model without it. Keep the independent input route available throughout.

For a keyboard that requires typing the displayed code, the local person must use that keyboard and its confirmation key as directed. Typing through the assistant's virtual keyboard or a different connected keyboard does not demonstrate the required physical device interaction. If the device appears already connected elsewhere, inspect the model-specific handoff requirement rather than automatically following a Forget instruction on the other host.

### Windows

Use the installed version's native Bluetooth controls to select the identified peripheral from available devices and complete the displayed pairing ceremony. [Microsoft's Windows pairing guide](https://support.microsoft.com/en-US/Windows/Hardware/bluetooth/pair-a-bluetooth-device-in-windows) describes discovery, native selection and the separate Swift Pair notification route. Inspect the actual interface; do not insist on a button location from another Windows version.

If Swift Pair offers a nearby device, verify its physical identity and the same new-pairing authority before Connect. An unsolicited notification is not proof of ownership. Enabling an additional notification/setup feature is unnecessary when the existing native route works; do not grant unrelated prompts merely to shorten setup.

### After either route

Let one attempt settle, then inspect the exact entry and its current state. A timeout or vanished dialog is not proof of failure; reread the device list before retrying. Keep an existing entry and a new same-name entry distinct until their identity is established. Do not rename, delete or recreate them just to make the list look tidy.

If the code mismatches, the prompt targets another device, or physical confirmation is unavailable, cancel or leave that attempt held through the supported route. Do not approve an unseen prompt. If the request unexpectedly creates cloud/account-wide accessory association or needs a companion app, stop at that expanded scope and explain the required decision.

## 3. Verify the physical wireless path

Record time, host, physical device/channel, native connection state, check, observed result and whether the evidence is direct or supplied by the local person. Use only the function needed for acceptance.

- **Keyboard:** In a harmless local text field, have the user type a short invented phrase on the paired keyboard and exercise relevant ordinary keys. Ensure focus is in that field rather than a terminal, password box or message composer. Preserve current layout/accessibility settings; an unexpected character may be a layout issue rather than a failed radio connection
- **Mouse or trackpad:** Have the local person move the device, select a harmless control and use an ordinary scroll/gesture required by the request. Distinguish those physical actions from pointer movement produced by remote automation. Do not use a destructive button as the click check
- **Speaker or headset output:** Inspect the actual selected endpoint and use a brief approved harmless sound at a user-chosen comfortable level. Ask where it was heard; a moving volume meter does not prove sound reached the intended device. Avoid private audio or unexpectedly playing through a room speaker
- **Headset microphone:** Capture or test-call activation requires its specific authority. If requested, check the chosen input through an approved bounded method; otherwise report microphone use untested. Output success does not prove capture or remote receipt

Establish that the observed success used Bluetooth. A keyboard working while connected by a data cable or proprietary receiver can leave the wireless path unproved. With the user's agreement and a preserved control route, detach only the selected alternate connection when safe and model-supported, then repeat the relevant check. Do not unplug a shared receiver, dock or unrelated cable. If the route cannot be isolated without disruption, state that limitation instead of claiming wireless acceptance.

Keep functional evidence proportional. Basic typing does not establish every shortcut, login-screen support or all remote-session behavior. Ordinary playback does not certify call quality, latency, microphone support or every audio format. If pairing succeeds but a target app selects the wrong endpoint, preserve the working device relationship and continue only the authorized app-level diagnosis.

## 4. Verify reconnection only to the requested extent

Reopen the native device settings and confirm the intended remembered relationship remains. Explain the normal model-supported way to return to this host or channel. Keep remembering, connecting now and reconnecting after an interruption as separate results.

If a deliberate reconnect is part of the request, first preserve the independent control route and active work. Disconnect only the target through its supported control, or use the agreed peripheral power/channel action, then return and repeat the functional check. Record whether reconnection happened automatically or required a manual Connect action. Do not remove the bond to test an ordinary reconnect.

A reconnect during the current session does not prove behavior after reboot, sleep/wake or switching to another computer. Those observations require the actual event, a safe interruption and appropriate authority. Do not log out, reboot, move the device to another person's computer or interrupt a call just to complete a checklist. When a requested later observation remains necessary, keep that part pending until the agreed opportunity or a specific blocker; do not mark it passed from settings alone.

## Recovery and stopping conditions

[Microsoft's connection troubleshooting](https://support.microsoft.com/en-us/windows/hardware/bluetooth/troubleshoot-bluetooth-not-connecting-in-windows) identifies pairing mode, range, battery and broader system causes as different possibilities. Choose a check supported by the observed boundary rather than executing its entire repair list.

- **Not discovered:** Recheck the exact model's mode, intended channel, available power and existing host attachment. Request a fresh pairing-mode action only when it does not overwrite an unapproved relationship. Absence alone does not prove hardware failure
- **Remembered but not connecting:** Inspect current channel and any known competing connection before considering removal. Do not repeatedly create new bonds or reset all radios
- **Pairing uncertain:** Inspect the current native entry and physical status before another attempt. Preserve the actual outcome as unknown if they cannot be reconciled
- **Paired but no required function:** Separate Bluetooth connection from alternate transport, app selection and supported device capability. Keep a working unrelated input/audio path intact
- **Removal or re-pair genuinely needed:** Explain the exact host/device entry and channel affected, how control will be maintained, and that a new pairing may be required. Obtain applicable confirmation before deleting a security relationship and again before creating new persistent trust. Never delete raw key stores or use a factory reset as generic cleanup
- **Wrong device or unexpected relationship:** Stop further input/audio transmission, report what happened, and use only the authorized exact-device disconnect/removal route. Removing a local entry does not prove that another host's entry or an account-wide association was removed
- **Control or recovery lost:** Stop further remote actions, state the known current condition and use the agreed local recovery. Do not send blind keystrokes or claim restoration without readback

Disconnect and Forget/Remove are not interchangeable. Apple's [Bluetooth guide](https://support.apple.com/en-gb/guide/mac-help/blth1004/mac) distinguishes disconnecting a device from forgetting it so that it must be connected again for later use. Inspect equivalent behavior on the actual platform. Retain only non-secret before-state information; restoring a previous bond may require a new ceremony rather than restoration of a label.

Stop when the exact intended relationship and required wireless function are evidenced, the requested plan is delivered, or a specific identity, capability, permission or physical-observation blocker prevents the next step. Do not claim a device working from a paired label or claim complete recovery while the only usable input remains disconnected.

## Deliver a small usable handoff

For a simple success, a few lines are sufficient:

- Host and identified physical device/channel; new pairing or reused relationship
- What changed, what remains remembered, and any effect on an earlier host/channel
- Actual wireless function checked, evidence source and reconnection condition observed
- The supported reconnect/disconnect route and any required local action
- Remaining app, microphone, alternate-transport or later-session check, with the smallest next step

Use precise status such as prepared only, paired with function unverified, wireless use checked, or checked with a stated remaining requirement. Keep private device identifiers, nearby-device lists, pairing codes and unrelated account details out of shareable records. A pairing record is not a security certification or a promise of future reliability.

## Fictional, unexecuted illustration

A fictional user wants a three-channel Bluetooth keyboard connected to a laptop while keeping channel 1 for an existing desktop. The exact model's manual supports selecting a separate channel for a new host. The laptop's built-in keyboard and trackpad remain available. The user chooses an unused channel 2 and approves the new persistent pairing at action time.

The proposed sequence would put only channel 2 into its documented pairing mode, match the physical keyboard to the native entry, and have the user complete the on-screen code on that keyboard. It would then ask the user to type an invented phrase in a harmless local field with any alternate data connection safely excluded. A subsequent approved channel-away-and-back check would support only that observed reconnection; reboot behavior would remain untested. Channel 1 would not be erased merely because the desktop is absent.

This is an invented decision illustration, not a completed setup. No device, radio, computer, account, pairing code, input field, audio path or connection was accessed or operated for it.
